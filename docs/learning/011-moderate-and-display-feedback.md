# 011：为什么评论审核通过后才能公开

日期：2026-11-02

## 评论审核闭环

访客提交反馈后，记录默认是 `PENDING`。管理员在 `/admin/feedback` 集中查看反馈，并把它改为 `APPROVED` 或 `REJECTED`。公开文章详情只查询 `APPROVED`，因此待审核和被拒绝的内容不会泄露到访客页面。

## 为什么审核操作还要再次鉴权

隐藏后台按钮或保护后台页面并不能保护 Server Action。攻击者可以绕过页面直接构造写入请求，所以“通过”和“拒绝”操作都会独立调用 `requireAdmin()`。只有持有有效管理员 Session 的请求才能修改审核状态。

## 为什么拒绝后不直接删除

`REJECTED` 可以保留审核记录，帮助管理员知道一条评论已经处理过，也便于误操作后重新通过。如果直接删除，就无法区分“从未收到”和“收到后拒绝”。

## 评分的展示规则

系统不计算文章平均评分，只展示每条已通过评论自己的 `0～5` 星评分。这样既保留了访客对文章的明确反馈，也避免用少量评论汇总出可能具有误导性的文章总分。

`0` 星是合法评分，会正常保存，并在审核通过后以五颗空星展示。

## 为什么公开查询在服务端过滤

服务端查询阶段直接加入 `status = APPROVED`。如果把所有评论发给浏览器，再依靠 CSS 或前端代码隐藏，访客仍然可以从页面源码或网络请求中看到未审核内容。

## 当前实现边界

- 后台优先展示待审核反馈，之后展示已经处理的反馈。
- 管理员可以纠正审核结果：已拒绝的反馈可以重新通过，已通过的反馈也可以改为拒绝。
- 每次状态改变都会记录新的 `reviewedAt`，并刷新后台概览、审核列表和对应文章页面。
