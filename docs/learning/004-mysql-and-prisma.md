# 004：把文章从代码迁移到 MySQL

日期：2026-11-01

## 为什么要迁移

前一阶段的文章保存在 `lib/articles.ts` 数组里。每次新增或编辑文章都需要修改代码，这不符合 CMS 通过后台管理内容的目标。本阶段把文章迁移到 MySQL，页面只负责查询和展示。

## 当前数据链路

```text
MySQL Article 表
→ Prisma Client
→ lib/articles.ts 查询函数
→ 首页或文章详情页
```

`lib/articles.ts` 不再保存文章内容，只保留公开查询规则。首页调用 `getPublishedArticles()`，详情页调用 `getPublishedArticleBySlug()`，两者都只查询 `PUBLISHED` 状态。

## Prisma 在项目中的作用

Prisma 把 `prisma/schema.prisma` 中的数据模型映射成 MySQL 表，并生成带类型的查询客户端。迁移文件记录表结构如何变化，使本地和服务器可以应用同一套数据库结构。

## 为什么 slug 要有唯一索引

详情页通过 slug 查找文章。如果两篇文章使用同一个 slug，它们会对应同一个网址，系统无法确定展示哪一篇。因此数据库使用唯一索引从源头阻止重复值。

## 为什么给 status 和 publishedAt 建联合索引

公开文章列表经常需要“筛选已发布文章，再按发布时间排序”。联合索引与这个查询模式一致，文章数量增加后能减少数据库扫描的数据量。

## 这次遇到的问题

1. 本机的 `3307` 端口已被其他程序占用，Prisma 误连到了另一个 MySQL，出现账号验证失败。
2. 项目数据库改用 `3308` 后，Docker 容器成功绑定端口。
3. `prisma migrate dev` 需要影子数据库验证迁移，但应用账号没有全局建库权限。
4. 项目单独创建 `yangyang_cms_shadow`，迁移阶段使用本地 root 访问影子库，应用运行时仍使用权限较小的 `cms_user`。

这说明“认证失败”不一定是密码写错，也可能连接到了错误的服务；排查时要同时检查地址、端口、容器状态和账号权限。

## 验证结果

- Prisma Schema 校验通过。
- TypeScript 类型检查通过。
- 数据库包含 `2` 篇 `PUBLISHED` 文章和 `1` 篇 `DRAFT` 文章。
- `.env` 被 Git 忽略，公开仓库只保留不用于生产的本地示例配置。
