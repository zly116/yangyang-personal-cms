# 007：不修改代码也能创建文章

日期：2026-11-01

## CMS 闭环向前一步

文章最初写在代码数组中，后来迁移到 MySQL，但仍要通过 seed 脚本添加。本阶段增加后台创建表单，管理员可以填写内容并保存到数据库，开始具备真正的内容管理能力。

## 为什么默认强调保存草稿

发布会立即改变公开网站内容，属于影响访客的操作。表单同时提供“保存草稿”和“发布文章”，页面文案优先引导先保存草稿，减少内容未检查就公开的风险。

- 保存草稿：`status = DRAFT`，`publishedAt = null`。
- 发布文章：`status = PUBLISHED`，`publishedAt = 当前时间`。

## 为什么前端和服务端都要校验

HTML 的 `required`、`maxLength` 和 `pattern` 可以快速提醒管理员，改善填写体验，但这些限制可以被绕过。真正写入数据库前，Server Action 会再次校验必填内容、长度和 slug 格式。

原则是：前端校验服务体验，服务端校验负责安全和数据正确性。

## 为什么 Server Action 还要验证 Session

表单位于后台不代表提交请求一定来自后台页面。别人可以绕过页面直接构造请求，因此 `createArticleAction()` 开始时再次调用 `requireAdmin()`，未登录请求不能写入文章。

## 为什么 slug 必须唯一

每篇文章通过 `/articles/[slug]` 访问。重复 slug 会让两篇文章争用同一个网址，因此数据库唯一索引是最终保障。服务端捕获 Prisma 的 `P2002` 唯一约束错误，再返回管理员看得懂的提示。

## 为什么校验失败时保留表单内容

文章正文可能很长。如果出现 slug 重复等错误后清空全部输入，管理员需要重写内容。React 的 `useActionState` 接收服务端错误结果，页面不跳转，因此浏览器保留已填写字段。

## 当前限制

- 正文目前按纯文本显示，尚未接入 Markdown 或富文本编辑器。
- 没有自动生成 slug，管理员需要手动填写。
- 还不能编辑、发布已有草稿或删除文章。
- 尚未记录文章操作审计日志。

这些限制将在后续批次根据项目价值逐步处理。
