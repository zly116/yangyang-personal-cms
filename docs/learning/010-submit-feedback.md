# 010：访客评分和评论为什么先进入待审核

日期：2026-11-01

## 数据模型选择

第一版把评分和评论保存在同一条 `ArticleFeedback` 记录中，因为它们来自同一次访客反馈，并且需要一起审核。字段包括文章、昵称、正文、0～5 星、审核状态、匿名访客哈希和创建时间。

如果未来允许“只评分不评论”、允许修改评分或需要复杂评分去重，可以再拆成独立的评分表和评论表。

## 为什么默认状态是 PENDING

公开评论可能包含垃圾广告、攻击性内容、隐私信息或恶意链接。访客提交后默认进入 `PENDING`，只有管理员审核为 `APPROVED` 后才能公开。`REJECTED` 用于保留审核结果，而不是反复显示为待处理。

## 为什么不能只依赖前端限制

提交 Action 会重新验证：

- 目标文章必须存在、已发布且不在回收站。
- 昵称可以不填，不填写时由服务端保存为“匿名访客”；填写时长度为 2～30。
- 评论长度为 5～1000。
- 评分必须是整数且位于 0～5；0 星是明确的最低评分，会与评论一起保存和展示。

即使访客绕过表单直接构造请求，也不能向草稿或回收站文章写入公开反馈。

## 基础防重复策略

浏览器第一次提交时获得随机访客 Cookie。数据库不保存原始 Cookie，只保存 SHA-256 哈希。同一访客对同一篇文章 10 分钟内不能再次提交。

这能减少误操作和普通刷屏，但不是绝对防刷：清除 Cookie、换浏览器或使用自动化工具仍可绕过。上线前可叠加反向代理 IP 限流、验证码和行为风控。

## 蜜罐字段

表单含一个正常用户看不到也不会填写的 `website` 字段。简单机器人经常自动填写所有输入框；服务端发现该字段有值时，不写入数据库，但返回普通成功结果，避免向机器人暴露拦截规则。

## 隐私与安全

- 不要求访客注册，不收集邮箱；昵称在前端明确标记为选填，留空时服务端保存为“匿名访客”。
- 数据库只保存随机访客标识的哈希。
- 评论当前作为普通文本由 React 渲染，React 会转义 HTML，避免直接执行访客提交的脚本。
- Cookie 使用 `HttpOnly` 和 `SameSite=Lax`；生产环境通过 HTTPS 时启用 `Secure`。

## 后续完善方向

- IP/全站级限流和验证码尚未实现。
