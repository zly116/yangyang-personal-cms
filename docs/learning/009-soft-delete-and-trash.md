# 009：为什么文章删除使用回收站

日期：2026-11-01

## 三种删除方式

物理删除直接执行 `DELETE`，实现简单，但误删后难以恢复。把 `TRASH` 加入发布状态虽然直观，却会覆盖文章原来的草稿/已发布状态。项目最终选择软删除：新增可空的 `deletedAt` 字段。

- `deletedAt = null`：普通文章。
- `deletedAt = 某个时间`：已移入回收站。

文章原来的 `DRAFT` 或 `PUBLISHED` 状态不变，所以恢复时无需额外记录原状态。

## 为什么所有普通查询都要过滤 deletedAt

软删除不会从数据库移除记录。如果公开首页、详情页、后台统计、文章列表或编辑页漏掉 `deletedAt = null` 条件，回收站文章可能再次出现或被编辑。

因此本次修改扫描了所有文章查询入口，并为普通查询统一增加删除条件。回收站页面则反向查询 `deletedAt IS NOT NULL`。

## 恢复已发布文章的影响

软删除保留原发布状态。恢复原状态为 `PUBLISHED` 的文章时，它会立即重新出现在公开网站。因此回收站不能只写“恢复”，而要提示“恢复并重新公开”，并在提交前再次确认。

## 为什么回收站中的 slug 仍被占用

软删除记录仍然存在，数据库唯一索引也仍然生效。这样恢复文章时不会发现 slug 已被新文章占用。代价是管理员不能立即用同一 slug 创建另一篇文章。

## 为什么第一版不提供永久删除

永久删除不可逆，而当前项目还没有完成自动备份、操作审计和关联数据处理。先完成可恢复回收站能满足内容下线需求，并降低误操作风险。永久删除应在评论等关联表出现后，连同外键策略和备份恢复一起设计。

## 安全边界

移入和恢复操作都会在 Server Action 内调用 `requireAdmin()`。浏览器确认框用于防止管理员误点，但它可以被绕过，不能代替服务端身份验证。
