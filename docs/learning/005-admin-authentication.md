# 005：为什么管理后台选择数据库会话

日期：2026-11-01

## 需求

公开网站允许任何访客阅读，但管理后台只能由管理员访问。只隐藏后台链接没有安全作用，因为别人仍可手动输入 `/admin`，因此权限必须在服务端验证。

## 方案比较

### 数据库会话

登录成功后生成随机令牌，浏览器保存令牌，数据库保存令牌的 SHA-256 哈希、所属用户和过期时间。每次访问后台时，服务端查询会话是否存在且未过期。

优点是服务端可以立即撤销某次会话，退出登录也能马上失效。缺点是每次验证通常需要查询数据库。

### JWT

JWT 可以携带用户信息并由签名验证，不一定每次查询会话表，适合多个服务共享身份或开放 API。缺点是已签发令牌在到期前不容易立即撤销，还要处理刷新令牌、密钥轮换等问题。

第一版只有一个网站后台，不需要跨服务认证，因此选择结构更直接、容易撤销的数据库会话。

## 密码为什么不能明文保存

数据库可能因漏洞、误配置或备份泄露而暴露。如果保存明文，攻击者会直接得到管理员密码。本项目使用带随机盐的 `scrypt` 哈希；登录时对输入密码做同样计算，再以固定时间方式比较结果。

哈希不是加密：项目不需要恢复原密码，只需要验证输入是否一致。

## Cookie 为什么使用 HttpOnly

浏览器通过 Cookie 自动携带会话令牌。`HttpOnly` 阻止普通前端 JavaScript 读取这个 Cookie，降低脚本漏洞窃取会话令牌的风险。`SameSite=Lax` 也能降低部分跨站请求风险，生产环境还会启用 `Secure`，只允许 HTTPS 传输。

## 为什么数据库不保存原始会话令牌

浏览器持有随机原始令牌，数据库只保存它的 SHA-256 哈希。请求到来时，服务端哈希 Cookie 再查询会话。这样即使会话表泄露，攻击者也不能直接把数据库中的值当作 Cookie 使用。

## 当前仍未闭环

- 登录失败次数限制和 IP/账号限流尚未实现。
- 生产环境 HTTPS 尚未配置。
- 会话定期清理任务尚未实现。
- 管理员改密和强制退出所有设备尚未实现。

这些不是第一批登录闭环的阻塞项，但上线前必须处理或明确接受风险。
