# 012：为什么个人介绍也应该由 CMS 管理

日期：2026-11-02

## 从写死内容到可管理内容

最初主页中的姓名、身份和自我介绍直接写在 React 代码里。每次修改都要编辑源代码，并重新构建和部署网站。这不符合 CMS 的目标：内容应该通过管理后台维护，而不是依赖程序员改代码。

现在个人资料保存在 MySQL 的 `SiteProfile` 表中。管理员通过 `/admin/profile` 修改资料，公开主页在服务端读取最新记录。

## 为什么只保存一条记录

当前网站只有一位所有者，不需要创建多份个人资料。系统约定使用固定的 `id = 1`，保存时使用 `upsert`：记录不存在就创建，已经存在就更新。这样不会因为重复保存产生多行资料，也不需要猜测主页应该使用哪一行。

如果未来发展为多作者博客，再把个人资料与管理员或作者账号建立关联。

## 为什么不用通用 key/value 配置表

键值表扩展字段方便，但所有内容都会变成没有明确类型的字符串，也容易写错键名。`SiteProfile` 使用结构化字段，每个字段的含义和长度清晰，更适合当前规模，也更容易使用 Prisma 校验和查询。

## 为什么服务端仍要校验

浏览器中的 `required` 和 `maxLength` 只能改善填写体验，攻击者可以绕过表单直接构造请求。因此保存 Action 会重新执行 `requireAdmin()`，并再次检查所有字段的空值和长度。

## 为什么第一版只允许普通文本

个人介绍暂时不接受 HTML。普通文本由 React 自动转义，能降低脚本注入风险，也避免第一版过早引入富文本编辑器、HTML 清洗和复杂的格式兼容问题。
